## 要件12: コスト最適化（AWS前提）

**ユーザーストーリー:** ユーザーとして、システムがAWS上で最小限のコストで運用されることを望む。なぜなら、個人利用のため運用コストを抑えたいから。

### 受入基準

1. システムはAWS上でコスト効率の高いアーキテクチャを採用しなければならない
2. システムはAWSの無料枠を最大限活用する設計でなければならない
3. システムは常時稼働するEC2インスタンスを必要としないサーバーレスアーキテクチャを検討しなければならない
4. ストレージを使用する場合、システムはアクセス頻度に応じた適切なストレージクラス（S3 Standard、S3 Infrequent Access等）を選択しなければならない
5. システムは実行時間とリソース使用量を最小化する設計でなければならない
6. 処理を分割することで、各Lambda関数のメモリを256MBに削減しなければならない（従来の512MBから50%削減）
7. Lambda実行時間は合計で89.9%削減され、月間3,175 GB秒（無料枠400,000 GB秒以内）でなければならない
8. Lambda関数の分割により、タイムアウト問題を解決し、大規模収集（2,700件）でも安定して実行可能でなければならない
9. Step Functions移行による追加コストは月間$0.04以内でなければならない
10. 月間状態遷移数は5,640回（無料枠4,000回を1,640回超過）でなければならない
11. 将来的にfetchとsaveを統合することで、状態遷移数を50%削減し、無料枠内（$0.00）に収めることを検討しなければならない
12. 月間総コストは$1.75以内（S3: $1.71、Step Functions: $0.04）でなければならない

**実装状況:**
- ✅ Lambda関数メモリ256MBに最適化
- ✅ Lambda実行時間89.9%削減
- ✅ Step Functions追加コスト$0.04/月
- ✅ 月間総コスト$1.75以内

## 要件14: テストとQA

**ユーザーストーリー:** ユーザーとして、システムが十分にテストされ、高品質であることを望む。なぜなら、データの正確性と信頼性が投資判断に直結するから。

### 受入基準

1. システムはすべてのビジネスロジックに対してユニットテストを実装し、コードカバレッジ80%以上を維持しなければならない
2. システムはプロパティベーステスト（fast-check）を使用してCorrectness Propertiesを検証しなければならない
3. システムは統合テストを実装し、Lambda関数とAWSサービス間の連携を検証しなければならない
4. システムはE2Eテストを実装し、Webダッシュボードの主要機能を検証しなければならない
5. システムはCI/CDパイプラインでテストを自動実行し、テスト失敗時はデプロイを中止しなければならない
6. Lambda関数のユニットテストは以下のカバレッジを満たさなければならない：
   - 正常系: 基本的な成功シナリオ（1件、複数件、0件）、ページネーション処理、空データの処理
   - バリデーション: 必須パラメータの検証、数値範囲の検証、日付フォーマットの検証、日付範囲の検証
   - エラーハンドリング: Retryableエラー（ネットワークエラー、タイムアウト、5xx、429）、Non-Retryableエラー（404、400、バリデーションエラー）、部分的失敗
   - パフォーマンス: レート制限の動作確認、並列処理の動作確認、大量データの処理
   - データ整合性: 開示ID生成の一意性、date_partitionの正確性、連番の正確性
7. 統合テストは以下の要件を満たさなければならない：
   - LocalStack必須: DynamoDB、S3、Lambda環境をLocalStackで構築
   - 環境変数: `AWS_ENDPOINT_URL`、`DYNAMODB_TABLE`、`S3_BUCKET`を設定
   - 条件付き実行: LocalStack環境でない場合は`test.skip`でスキップ
   - テストケース: DynamoDBへのデータ保存確認、S3へのPDFアップロード確認、実行状態の遷移確認、複数データの一括保存確認、エラー時の適切なハンドリング確認
   - タイムアウト設定: 統合テストは30秒のタイムアウトを設定
8. システムはテスト実行環境として以下の選択肢をサポートしなければならない：
   - ローカル実行: 開発者のマシン上でDocker + LocalStackを使用した統合テスト実行
   - GitHub Actions: CI/CD環境でのテスト自動実行（PRマージ前の品質ゲート）
9. GitHub Actions環境では以下の要件を満たさなければならない：
   - ユニットテストと統合テストを並列実行し、テスト時間を短縮する
   - LocalStackをGitHub Actions Servicesとして起動し、統合テストを実行する
   - `node_modules`とLocalStackイメージをキャッシュし、ビルド時間を短縮する
   - テスト失敗時はPRマージをブロックする
10. テストスクリプトは以下のように分離しなければならない：
    - `npm run test:unit`: ユニットテストのみ実行（開発時の高速フィードバック用）
    - `npm run test:integration`: 統合テストのみ実行（LocalStack必須）
    - `npm run test:e2e`: E2Eテストのみ実行（LocalStack + Webダッシュボード必須）
    - `npm test`: すべてのテストを実行（CI/CD環境用）

## 要件15: DR/バックアップ戦略（最小限の実装）

**ユーザーストーリー:** ユーザーとして、最小限のDR/バックアップ機能を持つことで、誤操作やシステム障害からの復旧を可能にしたい。なぜなら、データ再収集には時間がかかり、コストとのバランスを取りたいから。

### 受入基準

1. システムはDynamoDBのPoint-in-Time Recovery（PITR）を有効化し、過去35日間の任意の時点への復元を可能にする
2. システムはS3バケットのバージョニングを有効化し、誤削除や上書きからの復元を可能にする
3. システムはCloudTrailログを7年間保持し、監査証跡を記録する
4. データ損失時は、TDnetから再収集することで復旧する方針とする（バックアップからの復元は補助的手段）
5. システムは定期的なバックアップテストを実施しない（コスト削減のため）

### 実装状況

- ✅ DynamoDB PITR: 有効化済み（foundation-stack.ts）
- ✅ S3バージョニング: 有効化済み（foundation-stack.ts）
- ✅ CloudTrail: 7年間保存設定済み（monitoring-stack.ts）
- ✅ 再収集スクリプト: fetch-data-range.ps1, manual-data-collection.ps1

### 理由

- **最小限のコスト**: AWS無料枠内で運用しつつ、基本的なDR機能を確保
- **データ再収集可能**: TDnetから過去データを再収集できるため、高度なバックアップは不要
- **誤操作対策**: バージョニングとPITRで人的ミスからの復旧を可能に
- **監査証跡**: CloudTrailで操作履歴を記録（セキュリティ要件13と連携）

### 注意事項

本番環境で使用する場合や、企業向けに展開する場合は、以下の追加対策を検討すること：
- クロスリージョンレプリケーション
- 定期的な復旧テスト
- バックアップ自動化（AWS Backup）
- RPO/RTO目標の設定

## 要件20: 管理画面のパフォーマンスとスケーラビリティ

**ユーザーストーリー:** ユーザーとして、管理画面が高速に動作し、大量のデータを扱えることを望む。なぜなら、運用効率を最大化し、ストレスなくシステムを管理したいから。

### 受入基準

#### レスポンス時間
1. ダッシュボードホームの初期表示は3秒以内に完了しなければならない
2. 統計情報の更新は5秒以内に完了しなければならない
3. 検索・フィルタリング結果の表示は2秒以内に完了しなければならない
4. 個別レコードの詳細表示は1秒以内に完了しなければならない
5. PDFプレビューの表示は3秒以内に完了しなければならない

#### データ処理
6. システムは10万件以上のデータを扱えなければならない
7. 統計情報の計算は過去30日分のデータに限定し、パフォーマンスを最適化しなければならない
8. 検索結果はページネーション（1ページ50件）で表示しなければならない
9. 大量データのエクスポート（CSV、JSON）は非同期処理で実行し、完了時に通知しなければならない

#### キャッシング
10. 統計情報はCloudFrontまたはAPI Gatewayでキャッシュし、5分間有効としなければならない
11. 静的アセット（CSS、JavaScript、画像）はCloudFrontでキャッシュし、24時間有効としなければならない
12. DynamoDBクエリ結果はLambda内でメモリキャッシュし、1分間有効としなければならない

#### スケーラビリティ
13. システムは同時アクセス数10ユーザーをサポートしなければならない
14. Lambda関数の同時実行数は5に制限し、コストを最適化しなければならない
15. API Gatewayのレート制限は100リクエスト/秒に設定しなければならない

#### コスト最適化
16. 管理画面の追加コストは月間$0.50以内でなければならない
17. CloudFrontの使用量は無料枠（50GB転送/月）内に収めなければならない
18. Lambda実行時間の増加は月間+500 GB秒以内（無料枠内）でなければならない
